02 / 从小数据包到一次参数更新

Microbatch很小，更新的batch可以很大。

microbatch是一次送进流水线的小数据包；global batch是用于一次参数更新的全部数据。前向与反向会执行多次，参数更新只发生一次。

全局batch = DP × m × b = 2 × 8 × 2 = 32条序列b：microbatch大小；m：每副本在一次更新前处理的microbatch数。本例每个副本处理16条不同序列，两个副本合计32条。

沿着时间看一次更新

单独打开时间线 ↗

先分清三个数量

  1. 一个microbatch：2条序列。这2条序列由一份模型副本的4张卡合作计算，先经过前20层，再经过后20层。
  2. 每副本一次更新前：8个microbatch。共16条序列。每个microbatch都要完成前向、计算loss和反向，并累积参数梯度。
  3. 全局batch：32条序列。副本A和副本B读取不同文本，两个副本的梯度同步后，更新一次参数。TP和PP不增加独立样本数。

若每条序列长2048 tokens，一次更新使用65536 tokens。配置中的batch_size不一定等于global batch，需确认它表示的是每进程装载量还是全局有效batch。

怎样读这张时间线

F1表示microbatch 1的前向，B1表示它的反向；G是数据并行的梯度同步，U是参数更新。副本A和B中相同编号的microbatch对应不同文本。

  • 0→1：前段做F1；后段尚未收到激活，等待流水线填充。
  • 1→2：前段做F2，同时后段做F1。不同段处理不同microbatch。
  • 3→4：前段做B1，同时后段做F2。前向与反向已经交错，但参数还未更新。
  • 17→18：后段已完成8个microbatch的回传，开始后段DP同步；前段同时做最后一次B8。
  • 18→19：前段完成回传，开始前段DP同步。最后等待必要同步完成。
  • 19→20：各卡更新自己负责的参数分片，完成这一次全局batch的训练。

这是一个便于阅读的同步1F1B安排：假设前后向等长，将每段DP同步合并为一个方块，未单独展开逐层TP通信和逐microbatch的PP传输耗时。真实实现通常按梯度桶通信，并可与最后的反向计算进一步重叠。

反向8次，参数只更新1次

1F1B指预热后交替执行前向和反向，不表示每次反向就执行optimizer.step。第一次反向结束时，梯度写入累积缓冲；后续microbatch继续贡献梯度，而参数保持本次更新开始时的版本。

若每个microbatch的loss已经对其中2条序列取平均，梯度可以写成：

gA = (gA1 + … + gA8) / 8
gB = (gB1 + … + gB8) / 8
g = (gA + gB) / 2

最后使用全局平均梯度g执行一次优化器更新。这些式子针对相同长度、相同权重的microbatch；若有效token数不同，平均方式也需要按定义调整。

在普通DDP里，可用no_sync()让前几个microbatch先累积，最后再同步。它延后的是DP梯度同步，不能省略模型计算所需的TP或PP通信。

三种通信，传的内容不同

通信传什么什么时候发生
TP · 层内协作分片激活、部分结果，以及反向所需的对应梯度。包含在每个F或B方块内部，按具体层的切分方式发生。
PP · 相邻段传递前向传中间激活，反向传对激活的梯度。每个microbatch经过流水线边界时发生。
DP · 跨副本同步同一位置参数分片的梯度，例如GPU 0↔4、GPU 1↔5。本图按每段完成累积后启动；真实实现可分桶并重叠通信。

为什么要把前后向交错？

如果先执行所有microbatch的前向，再统一反向，就要保留更多待回传的激活。1F1B让部分反向更早开始；某个microbatch完成回传后，其不再需要的激活可以更早释放。

流水线仍然存在填充、排空和等待，图中的留白就是这些等待。因此多卡数量、microbatch数量和最终加速比不能直接划等号。
